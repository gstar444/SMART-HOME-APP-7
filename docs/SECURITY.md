# Security notes

What is protected, how, and – more important – what is **not**.

## 1. Assets and the controls around them

| Asset | Where it lives | Protection |
|---|---|---|
| Board access token | app: Android Keystore-backed secure storage; board: only `SHA-256(token)` in `/config.json` | 256-bit random token generated by the app (`Random.secure()`); constant-time compare; failed-login lock-out; rotation endpoint; never in a URL, never logged |
| Broker password (app) | app secure storage only (never shared_preferences; auto-backup disabled) | validated settings: TLS only, host name not IP, no way to disable certificate checks |
| Broker password (board) | board `/config.json` (**plaintext**, see §4) | per-board login; accepted only over the authenticated local API; never returned (`hasPassword` only) |
| Wi-Fi password (board) | board `/config.json` (**plaintext**, see §4) | same; the v3 copy in NVS is erased after a verified migration |
| Claim code | printed once on the serial console; stored on the board only until Wi-Fi is confirmed | 50 random bits from the hardware RNG; 5 wrong tries → 5 min lock; deleted afterwards |
| Relay/lock state | the board | local token, or allow-listed cloud commands (below) |

## 2. Provisioning without any shared password

There is no default hotspot password, API key or token in the source. A board with no owner generates a random claim code at
first boot (and after a credential reset). The code is the WPA2 password of the setup hotspot **and** proof of physical
access for `POST /api/v2/claim`, which stores the hash of a token the app just generated. Whoever can read the USB serial
console owns a fresh board – that is the trust anchor, as with most hobby devices. If you can not accept that, enable
flash encryption and disable the serial output (§4).

## 3. Threat analysis

| Threat | What happens | Residual risk |
|---|---|---|
| Stranger on the LAN sends relay commands | Needs the token (401). 5 failures/minute → 60 s lock-out. Old unauthenticated v3 routes answer 410. | The lock-out is global, so a LAN attacker can keep the legitimate app out (denial of service). The stock `WebServer` buffers a request body before our size check runs, so an oversized body can exhaust memory. Both need LAN access. |
| Sniffing the token on the LAN | The local link is **plain HTTP**: on a network where others can capture frames (open/shared Wi-Fi, a compromised device on the same network) the Bearer token can be read. | Use WPA2/WPA3 with a private password, keep boards off guest networks, rotate the token (*Boards → ⋮ → Rotate token*) after any doubt, never port-forward port 80. Local TLS with a pinned self-signed certificate is the natural next step and is **not** implemented. |
| Web page triggers a relay (CSRF) | Writes are POST + JSON + Authorization header, no CORS headers, no OPTIONS: browsers can not make that cross-origin request. | none known |
| Eavesdropper/man-in-the-middle on the cloud link | TLS 1.2+ with a **pinned root** (ISRG Root X1 / DigiCert Global Root G2 / your PEM); `onBadCertificate` and the board's CA check always reject. Verified by SHA-256 pin at build time (`gen_ca_header.py`). | Needs a correct clock (board waits for SNTP). Host-name verification is done by the TLS stack when connecting by name – **confirm on hardware** (CLOUD_SETUP §6). Providers may change their chain; then use the "extra CA" override. |
| Stolen/leaked **app** broker login | Attacker can read all topics of that home on plans without per-topic ACLs, and can send commands. A board runs only: `set` (refused if `remote:false`, locks can be locked but not unlocked unless allowed), remote-only `scene`, `dnd`, and – if `remoteConfig` – room names and device name/room/icon. It can **not** change pins, Wi-Fi, credentials, token, schedules, automations or firmware. | They can still switch devices you marked remote. Revoke the login at the broker; set `remote:false` on anything that must never be cloud-controlled. |
| Stolen **board** broker login | Attacker can publish fake state for that board id and read its commands. | Per-board logins + per-topic ACL (paid HiveMQ, EMQX) confine it to that board's topics. |
| Replay of a captured command | TLS prevents capture on the wire. A command id is executed at most once (16-entry memory) and answered `dup:true`; commands are absolute states, so a replay is idempotent. | There are no timestamps (the board's clock is not trustworthy at boot), so a replay of an id that has fallen out of the 16-entry memory would be executed again. With broker credentials an attacker could just send a new command anyway. |
| Malicious or broken configuration | Only the authenticated local API can change config. Strict validation: GPIO policy per chip, duplicate pins, ids/lengths, mqtt port 8883 for presets, automation loops, **never unlock**, no boot-on for heater/siren/lock. A file that fails to load is repaired or its rules disabled, never trusted blindly; a file from a *newer* firmware is never overwritten. | A valid but foolish configuration is still valid (for example a very long schedule list). |
| Automation runaway | cooldown ≥ 5 s per rule; ≤ 6 firings/min in total; rule can not act on its own trigger; first action on a device wins; manual commands (10 s) take precedence. | Indirect loops are throttled, not detected. |
| Physical access | USB serial gives the claim code on an unclaimed board; BOOT held 8 s wipes Wi-Fi/broker login/token (not devices/rules) and starts claiming again. Reading the flash chip reveals Wi-Fi and broker passwords (§4). | Inherent without flash encryption; protect the enclosure. |
| Android app | No secret in code, prefs, or logs; `allowBackup=false`; no cleartext policy for WebView; camera URL is user-chosen and must be http(s). | The camera WebView runs JavaScript from whatever URL *you* configured. A rooted/compromised phone defeats any app-level protection. |

## 4. What software can not do, and the ESP32 hardware features that matter

* **Secrets at rest on the board.** The config (Wi-Fi password, broker password) is a plain file on LittleFS. Anyone who can
  read the flash can read them. The token is stored only as a hash. To protect the rest, use the chip's security features
  – **none of which this project enables**, because they are irreversible (eFuses) and depend on your board:
  * **Flash encryption** (ESP32, S3, C3) – encrypts flash contents incl. LittleFS; production mode is one-way and complicates
    re-flashing. Prerequisite for protecting the passwords.
  * **Secure Boot** (V2 on S3/C3 and newer ESP32 revisions; V1 on older ESP32) – only signed firmware boots; matters once
    you add OTA. The ESP32 variant/revision determines what is available.
  * Disabling UART download mode / JTAG via eFuses, and not printing the claim code, if serial access is a concern.
  Follow Espressif's documentation for your exact chip revision before burning any eFuse.
* **No hardware root of trust for the claim code** – it is random per boot, not burned at the factory.
* **Time.** TLS validation and schedules need a correct clock; if SNTP is blocked, the cloud never connects.
* **Broker trust.** The broker operator can see and alter traffic metadata (and everything, if you used plan-wide credentials).
* **Not implemented in this phase** (so not attack surface): OTA updates, BLE provisioning, Telegram, voice assistants, AI commands.
  The earlier brief's OTA/Secure-boot items remain future work.

## 5. Logging

Serial log lines contain board ids, host names, MQTT/TLS error codes and counts. They never contain the Wi-Fi password, broker
password, token or token hash. The only secret ever printed is the claim code while the board is waiting to be claimed. The app
does not log credentials or tokens.

## 6. Reporting / hardening checklist for a deployment

- [ ] Private WPA2/WPA3 Wi-Fi; boards not on a guest network; port 80 not forwarded.
- [ ] One broker login per board and one for the app; per-topic ACL if your plan allows.
- [ ] `remote:false` on locks and anything that must stay local; `remoteConfig` off if not needed.
- [ ] Release APK signed with your own keystore (ANDROID_SIGNING.md).
- [ ] Decide on flash encryption (and secure boot once OTA exists) *before* deploying boards you can not easily re-flash.
- [ ] Rotate tokens after a phone is lost.
